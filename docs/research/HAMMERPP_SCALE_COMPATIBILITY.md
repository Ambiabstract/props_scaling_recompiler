# Hammer++ scale compatibility

Статус: базовая матрица утверждена для resolver PSR 2.0; расширенное исследование продолжается.

Дата снимка: 2026-08-21.

## Источник наблюдений

- Карта: `psr_scale_compatibility_01a.vmf`.
- Внешний read-only источник: `antenna_sdk2013/maps/psr_scale_compatibility_01a.vmf`.
- SHA-256 снимка: `af598164d2d04972a0a2d785fda6688e393ac4b24b177acb4d0919b08a7a12db`.
- Размер: 45 234 байта.
- Структурная проверка: VMF валиден.
- Активные `prop_static_scalable`: 35.
- Скрытые top-level блоки: 0.
- Тестовая модель во всех запросах: `models/apt/fsmit01.mdl`.

Во всех 35 сущностях поле `debug_string` имеет машинно-читаемый формат `effective_scale=<value>` и служит test oracle ожидаемого результата PSR для raw `modelscale`. Oracle уже включает два продуктовых преобразования: нижний clamp `0.01` и decimal `ROUND_HALF_UP` до сотых. Поле не является частью production/cache schema.

Для анализа исключения различаются три значения. Название `effective_scale` в `debug_string` относится к test oracle ожидаемого результата PSR и не означает поле production-модели:

| Raw `modelscale` | Hammer-compatible effective scale | PSR compile scale |
|---|---:|---:|
| `0.001` | `0.001` | `0.01` |
| `1.01` | `1.01` | `1.01` |
| `1.02` | `1.02` | `1.02` |
| `1.5` | `1.5` | `1.5` |
| `0.5` | `0.5` | `0.5` |

После Hammer-compatible parsing PSR сначала применяет `effective < 0.01 -> 0.01`, затем decimal `ROUND_HALF_UP` до сотых. Clamp защищает от практически бесполезных сверхмалых моделей; округление создаёт однозначный целый процент для generated identity. В production/cache PSR сохраняет raw и итоговый compile scale и выдаёт понятную диагностику; effective scale остаётся только test oracle и не сериализуется.

## Утверждённое базовое правило 2.0

По решению пользователя текущая матрица достаточна для production resolver 2.0. Resolver читает допустимый беззнаковый десятичный prefix до первого неподдерживаемого символа, а для отсутствующего, непригодного или неположительного результата использует fallback `1.0`. После этого применяются PSR clamp `0.01` и decimal `ROUND_HALF_UP` до сотых:

- `2,0 -> 2.0`;
- `1,5 -> 1.0`;
- `0,5 -> 1.0`;
- `0,01 -> 1.0`.

Правило реализовано в `psr.domain.resolve_compile_scale()` и покрыто всеми 35 oracle cases. Числовая identity вычисляется как точный целый `compile_scale * 100`, а в имени форматируется с минимальной шириной 3: `1 -> 001`, `50 -> 050`, `110 -> 110`, `1000 -> 1000`. Поэтому `1.095`, `1.1` и `1.104` дают одну identity `_scaled_110`, а `1.105` — `_scaled_111`. Формы `2,5`, `3,9`, `10,5`, `0,99`, знаки, exponent notation и экстремальные пределы остаются будущими regression-наблюдениями.

## Что ещё нужно добавить в regression-матрицу

### Парсинг

- отсутствующий `modelscale` и пустая строка;
- leading/trailing whitespace, если Hammer сохраняет его в VMF;
- `0`, `0.0`, `-0`, отрицательные значения и явный `+`;
- `1.`, `.5`, ведущие нули и несколько точек;
- exponent notation;
- числовой префикс с текстовым суффиксом и текстовый префикс с числом;
- дополнительные значения с запятой;
- `nan`, `inf` и аналоги, если Hammer позволяет сохранить их.

### Пределы

- значения непосредственно ниже, на уровне и выше `0.01`;
- дополнительные значения ниже `0.01`, подтверждающие единый нижний clamp;
- верхняя поддерживаемая граница выше `55`;
- поведение при overflow и очень длинных числах.

### Дополнительные границы округления

- добавить симметричные tie-cases наподобие `1.085`, не меняя утверждённый decimal `ROUND_HALF_UP`;
- проверить больше значений около нижнего clamp и очень больших целых процентов;
- фиксировать намеренное схлопывание визуально близких raw scales в одну generated identity.

## Рекомендуемый формат следующих отметок

Все текущие сущности уже используют основной машинно-проверяемый формат:

```text
effective_scale=1.0
effective_scale=0.01
```

Для ещё не измеренных будущих случаев можно временно использовать:

```text
unsupported=<краткое описание наблюдаемого поведения>
needs_measurement=<что именно сравнить>
```

При переносе карты в автоматические fixtures допустимы только окончательные записи `effective_scale=<value>`; временные отметки должны приводить к пропуску или явному отказу теста, а не превращаться в ожидаемое число.

## Условие завершения расширенного исследования

Расширенное исследование считается завершённым, когда для каждой добавленной строки известны raw value и test oracle, отдельно документированы расхождения с viewport и проверены дополнительные пределы. Базовое округление и детерминированный `_scaled_XXX` уже утверждены и реализованы.
